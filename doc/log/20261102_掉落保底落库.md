# 20261102 掉落保底落库

## 背景

`org.gms.server.loot.MobDropPityManager` 原来的绑定关系只放在静态 `Map` 里，重启即丢。
现在改为落库保存"当前生效的绑定"，解绑删行、角色删除时整体清理。

## 表结构

`sql/loot/mob_drop_pity.sql`

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT AUTO_INCREMENT | 主键 |
| `chr_id` | INT | 角色 ID |
| `mob_id` | INT | 怪物模板 ID |
| `item_id` | INT | 物品 ID |
| `personal_drop_percent` | DECIMAL(9,4) | 绑定时算出的个人爆率（百分比，1% 存 1.0） |
| `target_kills` | INT | 触发保底所需击杀数 |
| `kill_count` | INT | 当前已累计（未掉落）击杀数 |
| `created_at` / `updated_at` | TIMESTAMP | 绑定时间 / 最后更新时间 |

唯一键 `uk_chr_mob_item (chr_id, mob_id, item_id)`：一个角色对同一怪物同一物品只有一条保底，
重复绑定按唯一键覆盖（爆率、保底次数按最新一次重算，进度清零）。
辅助索引 `idx_chr_id (chr_id)`：按角色加载、按角色删除。

## 代码结构

| 位置 | 作用 |
|---|---|
| `org.gms.dao.entity.MobDropPityDO` | 实体（`@Table("mob_drop_pity")`） |
| `org.gms.dao.mapper.MobDropPityMapper` | `BaseMapper`（被 `@MapperScan("org.gms.dao.mapper")` 扫描） |
| `org.gms.dao.service.MobDropPityService` | Spring `@Service`，唯一键 upsert / 进度更新 / 删除 |
| `org.gms.server.loot.MobDropPityManager` | Spring `@Component`，对外仍是静态方法，内部走 `MobDropPityService` |

## 读写时机

| 动作 | 行为 |
|---|---|
| 首次访问某角色（查询/击杀/绑定） | `SELECT` 一次，把该角色全部绑定加载进内存缓存 |
| 开启/重复绑定 | `INSERT`，唯一键冲突则 `UPDATE`（覆盖爆率/保底次数，进度清零） |
| 解除绑定 | `DELETE` 该行 |
| 每次击杀（累计 +1 / 触发 / 自然掉落清零） | `UPDATE kill_count` |
| 删除角色 | `CharacterDataService#deleteAllCharacterData` 里按 `chr_id` 清理 |

## 注意

- 内存缓存按角色懒加载：没有绑定的角色也会缓存一个空 Map，避免每次击杀都查库；
  `MobDropPityManager#unload(chrId)` 可以主动丢弃缓存（下次访问重新加载）。
- 所有库操作都 try/catch：库挂了只打 `warn` 日志，游戏内的保底逻辑继续按内存跑，不会因为 DB 异常打断掉落流程。
- 非 Spring 环境下（`pityService == null`）自动退化为纯内存模式，行为与改造前一致。
