# GMS053 持久机器人需求说明

更新日期：2026-11-24

相关记录见 [问题讨论记录](053_持久机器人_问题讨论记录.md) 和 [BUG 修复记录](053_持久机器人_BUG修复记录.md)。

## 第一阶段的交付边界

第一阶段交付一个可自主单人游玩的真实角色。托管上线只是第一个子里程碑。其余子里程碑覆盖跨图、完整战斗、拾取、恢复与补给、养成、NPC 交互，最后实现自主任务。机器人独自在地图里时也要有真实的怪物行动、受伤和死亡复活。正常停服用原有存档，重启继续使用同一角色。玩家互动、组队、交易及社交玩法留到下一阶段。

能力覆盖按当前 053 真人入口逐项检查。遇到技能、地图或脚本的特例，明确记录支持状态和缺口，并用可复用的动作与策略补齐。首轮验收取代表性的职业和内容，后续用同一份清单扩大覆盖。

## 开发顺序与每步验收

| 子里程碑 | 要开发的能力 | 游戏内完成判定 |
| --- | --- | --- |
| 1.1 持久角色上线 | 从配置加载真实账号角色；注册世界、频道和地图；托管互斥；停服保存。 | 双客户端确认可见；在关闭托管并重启后，用原账号登录核对角色。1.1 已完成，用户实测确认 Bot 可见且正常站在地面。 |
| 1.2 导航与跨图 | 从平台、梯绳、落点构建走、跳、爬、落的图，按角色能力判可达；用 Dijkstra 或 A* 寻路。跨图复用正常传送口、回城卷及传送脚本入口，区分普通门与有条件门。地图坐标与 053 动作广播一起推进，录少量 053 样本验证动作编码。 | 同图走到上下层 NPC，往返城镇和练级图；不可达点或入口有失败原因，机器人能换目标。 |
| 1.3 战斗、怪物与死亡 | 服务端生成合法命中和伤害，复用玩家结算。统一普攻、近战技能、远程技能和魔法的动作入口，按技能族扩展攻击、增益、召唤等类型。接入无真人地图的怪物移动、仇恨、碰撞与受击，复用死亡和复活规则。 | 战士、法师和至少一类弹药职业各实测一种攻击；独自在线时怪物能追击和伤害机器人；死亡后能正常复活。 |
| 1.4 库存、恢复与回城补给 | 共用掉落归属、库存和金币结算；区分自然恢复、椅子恢复和药品效果；按 HP/MP 阈值用药。跨图去商店补药，支持卖杂物、装备更换与基础背包清理。 | 掉落只结算一次，坐椅与药品产生正确恢复，买卖和换装改变真实库存，补货失败有可执行的退路。 |
| 1.5 升级、AP/SP 与职业成长 | 监听或识别升级、转职和点数变化；按职业模板分配真实 AP 与对应技能书 SP；由数据推导技能前置，复用分配校验；覆盖职业转变、本职业装备和依赖技能书的技能。 | 战士和法师按各自模板分配，能够先补前置再加主攻，达上限时不扣点，停服后保留点数和技能等级。 |
| 1.6 NPC 与单人交互底座 | 走近 NPC，接入商店、转职和多轮脚本会话；支持继续、确认、菜单选择及退出。按单人内容需要增补反应堆、仓库、卷轴、宠物等能力，并记录哪些玩法单独跟踪。 | 一次普通 NPC 交互及一个带选项的脚本可正确执行；取消或换图后旧会话不可再提交。 |
| 1.7 自主任务（最后实现） | 复用已解析的任务条件及动作；将缺少的道具、击杀数、前置任务与进度映射成可执行目标；调用真实任务接交和脚本会话，支持选奖、扣除任务物品、容量和失败原因。 | 自主接交一个击杀任务、一个收集任务和一个带脚本或选奖的任务。错误 NPC、缺物品、满包、无效选项均不会发奖或错误推进。 |
| 1.8 全流程验收 | 把上述动作放入同一运行循环，记录决策、失败与退避，按双向包头清单补缺。 | 同一个机器人无人干预完成下方联调，并跨重启核对数据。 |

## 双向包头与单人覆盖

发送和接收枚举用于盘点功能。开发时还要核对接收项是否在 PacketProcessor 注册、对应发包是否在当前业务链触发，以及哪些状态原先由客户端计算或上报。表中是当前 053 枚举的代表项，覆盖验收时扩展到玩法级清单。

| 单人能力 | 客户端 → 服务端 | 服务端 → 客户端与验收重点 |
| --- | --- | --- |
| 出生、移动、换图 | MOVE_PLAYER 0x35、CHANGE_MAP 0x2F、CHANGE_MAP_SPECIAL 0x47 | SPAWN_PLAYER 0x65、MOVE_PLAYER 0x84、WARP_TO_MAP 0x4D。检查进出与坐标一致。 |
| 战斗与生存 | CLOSE_RANGE_ATTACK 0x59、RANGED_ATTACK 0x36、MAGIC_ATTACK 0x2E、SPECIAL_MOVE 0x51、TAKE_DAMAGE 0x2A、MOVE_LIFE 0x9D | 玩家攻击 0x87 / 0x8D / 0x93、DAMAGE_PLAYER 0x89、MOVE_MONSTER 0x97、怪物控制权 0xA4、死亡与属性更新。召唤类另核对控制入口。 |
| 拾取、背包和装备 | ITEM_PICKUP 0x89、ITEM_MOVE 0x62、USE_UPGRADE_SCROLL 0x65 | DROP_ITEM_FROM_MAPOBJECT 0xB8、REMOVE_ITEM_FROM_MAP 0xB9、INVENTORY_OPERATION 0x18。检查掉落归属、实际库存及装备。 |
| 治疗与补给 | USE_ITEM 0x63、USE_CHAIR 0x2D、CANCEL_CHAIR 0x2B、HEAL_OVER_TIME 0x67、USE_RETURN_SCROLL 0x64 | SHOW_CHAIR 0x91、STAT_CHANGED 0x23、换图。检查椅子、自然恢复和药水的数值来源，避免恢复重复计算。 |
| 升级和技能成长 | DISTRIBUTE_AP 0x66、DISTRIBUTE_SP 0x4D、USE_SKILL_BOOK 0x55 | STAT_CHANGED 0x23、UPDATE_SKILLS 0x2F。检查剩余点数、技能等级和上限。 |
| 商店、任务、地图对象 | NPC_TALK 0x23、NPC_TALK_MORE 0x21、NPC_SHOP 0x22、QUEST_ACTION 0x6B、STORAGE 0x20、DAMAGE_REACTOR 0x8C | NPC_TALK 0xC2、商店 0xD6 / 0xD7、UPDATE_QUEST_INFO 0x6C、仓库 0xD8、反应堆事件。检查真实脚本会话及金币、库存和任务更新。 |

### 单人扩展能力检查

- 补充检查地图交互，包括内部传送门、地图机关、反应堆、场景伤害、召怪袋和捕捉道具。需求来自具体地图和任务，可复用导航、道具使用与 NPC 会话。
- 补充检查战斗类技能，包括增益取消、召唤物移动、攻击与受击。召唤有独立上报链路，应该按技能族验证。
- 补充检查物品管理，包括仓库、卖出、弹药补充、卷轴、技能书和宠物。现有 PacketProcessor 的 ITEM_SORT、AUTO_DISTRIBUTE_AP 注册处为注释，覆盖时以当前真人可用入口为基线，也可复用底层玩家业务能力。
- 现金道具和商业系统另外标明用例。商城、MTS 和玩家交易留在首阶段验收范围之外，避免单人目标触发需要其他玩家或独立经济流程的操作。

仓库、强化、反应堆、召唤、宠物等属于单人可访问的扩展面。每项标记为已支持、部分支持或待支持，附代表地图或物品进行验证。快捷键、Ping、UI 窗口、客户端控制确认等属于客户端机制，由服务端适配器提供玩法所需语义即可。真人已有玩法为对照基线，变更优先提取可调用业务入口，保留原来的 Handler 输入和发包路径。

## 战斗和升级加点

通用的是动作和校验。武器、技能效果、资源消耗、技能行为和养成顺序随职业变化。AI 行为提交普攻或技能 ID，执行端读取角色及 SkillFactory 加载的实际效果，按攻击类型检查距离、武器、弹药、HP/MP、目标数、动作间隔和冷却。普攻也要按武器区分近战和远程。现有 AbstractDealDamageHandler 从客户端读目标和伤害，无客户端的机器人需要计算并生成攻击结果，再复用结算。战斗验收覆盖只有机器人在地图上的情况，并与真人同图时的表现对照。客户端控制权、受击和恢复的待核对细节见 [问题讨论记录](053_持久机器人_问题讨论记录.md)。

AP/SP 直接读实际剩余值与技能书。数据库种子默认是升级 5 AP、3 SP，真人可能受配置、新手自动加点、职业和转职规则影响。机器人只花服务端实际发放的点。AP 模板可用战士 STR:DEX 为 4:1、法师 INT:LUK 为 4:1；用确定性的配比进度处理不足一轮、积攒点数及重启，按现有属性上下限判断。SP 按配置目标逐点分配，通过现有 AssignAPProcessor / AssignSPProcessor 的业务规则落地，动作执行前重新核对剩余点与角色状态。

技能先把“允许学习”和“能主动使用”分开处理。

- Skill.wz 的 req 节点已经给出前置 ID 和等级。例：2001005 需要 2001004 达到 1 级。当前 SkillFactory 加载技能效果、动画等信息，Skill 未暴露 req，已核对的 AssignSPProcessor 也未验证该前置。计划在现有 WZ 技能加载时读取并公开不可变前置数据，让 AI 加点器按依赖顺序补点。技能不存在、职业不符、达到技能上限、技能书尚未开放或前置无法满足时，保留 SP 或评估下一候选。
- 当前 Skill.getAction() 表示动画相关信息，不能直接作为主动或被动的判断。按 WZ 的 action、hit、ball、效果与实际处理入口推导分类建议；由按技能 ID 配置的职业策略指定释放角色和优先级。首版人工配置代表职业的主攻、辅助和策略例外，前置和正常技能上限由数据读取，无需逐项录入。未知技能不自动释放。新增职业可复用已有攻击类型，特殊技能再加实现。
- 推荐模板为“主攻目标 → 自动补所需前置 → 主攻加到可达上限 → 按优先级补被动或辅助”。升级 HP/MP 的被动已被当前 levelUp 使用，允许模板把它放到主攻之前。已经升过级的角色遵守已有加点，不改写历史点数。

```java
// 设计示意：配置表达偏好，前置由 Skill.wz 提供。
record JobPolicy(Map<Stat, Integer> apWeights,
                 List<Integer> attackSkills,
                 List<SkillTarget> spPriority) {}

Optional<Allocation> nextPoint(CharacterSnapshot character, JobPolicy policy,
                               SkillCatalog catalog);
```

## 自主任务：条件、行动和奖励

仓库文件名为 Quest.wz/Check.img.xml 和 Quest.wz/Act.img.xml。QuestDataProviderV2 已读取它们并由 QuestRepository 提供 QuestV2。两份数据的 0 段用于开始，1 段用于完成。通过现有 WZ 资源选择流程拿到当前服务器的数据，避免机器人另解析一份 XML。

1. **选任务和找 NPC。** 读取 QuestV2 的 startReqs/completeReqs，利用 QuestRequirementType 和 QuestRequirementEvaluator 判断角色状态、等级、职业、前置任务、任务进度及重复条件等。NPC 类型还要传真实目标 NPC ID，并验证地图上的 NPC 和可达性；NpcChecker 本身只检查 ID。规划阶段可发现“条件满足、应前往 NPC”，执行时再调用和真人一致的接取、交付与脚本分支。
2. **把未满足条件转换为目标。** 缺击杀数就从任务进度找对应怪物；缺道具就用任务条件、实际库存及现有掉落表反查来源，并结合怪物分布与地图可达性决定去哪。缺前置任务先做可达的前置；脚本状态、限时和其他暂无法规划的条件记录具体阻塞原因。只复用 canStart/canComplete 能回答现在能否接交，不能告诉机器人下一步要打哪只怪或走去哪里。
3. **检查动作和奖励。** 复用 QuestActionType、QuestActionExecutor 和 QuestUtils.start/complete。开始和完成动作都可能发放或扣除道具，或变更职业、地图、技能等。完成条件满足后仍要验证实际奖励选项、角色资格、待扣物品和背包空间。ItemActionHandler 的选奖路径直接使用 extSelection 作为下标，AI 适配层应按当前可选列表验证缺失或越界选项。奖励实际随机结果由服务端决定。动作串行执行，重新读取任务状态及已提交结果，避免把资格校验误当作已发奖。
4. **执行多轮会话。** 现有 ScriptChecker 默认通过，实际特殊条件在脚本里执行。通过 QuestScriptManager / NPCScriptManager 获取继续、确认、菜单及输入请求，由任务策略提交合法选项；按任务记录已支持、需人工配置、暂无法自动执行。普通任务可以自动发现，复杂脚本允许单独配置路径或专用行为。

```java
// 设计示意：先给策略提供缺口，抵达后才执行真实接交。
QuestPlan plan = questAccess.plan(characterId, questId);
if (plan.isReadyToTurnIn() && npcAccess.canInteract(plan.npcId())) {
    questAccess.turnIn(characterId, questId, plan.npcId(), plan.rewardSelection());
}
```

## 最终联调场景

1. 用战士和法师分别验证职业策略；至少一个角色从城镇出发，跨图练级。
2. 独自面对可移动、可反击的怪物，按策略普攻或施法，拾取掉落并真实升级；分别核对 AP、SP、技能前置和技能消耗。
3. 自动喝红蓝药；药不足时回城，坐椅恢复并找商店 NPC 补货，之后返回原地图。另验证死亡复活和满包处理。
4. 机器人自行查出可接任务并找 NPC 接取，根据目标跨图击杀、拾取，回去交付并选择奖励。另跑通一个多轮 NPC 脚本。
5. 正常停服并关闭托管，用原账号登录，核对等级、经验、属性点、技能等级、金币、背包和任务记录。


## 模块边界

gms-ai 持有托管生命周期及未来的行为调度。gms-handler 持有真实 Character 与网络协议，以适配器提供角色加载、注册与存档，依赖单向指向 gms-ai。后续新增行为时注册独立实现，角色生命周期和已存在的动作可以照常使用。

```java
BotLifecycle lifecycle = new BotLifecycle(characterId -> openRealCharacter(characterId));
lifecycle.start(characterId);
// 地图与数据库仍在线时关闭
lifecycle.close();
```

后续每轮由各行为基于状态快照提出候选，选择一个可执行动作。低血时中断移动补给，拾取完成后继续原目标。正在结算的购买或拾取先完成，再切换动作。

## 子里程碑 1.1 验收

2026-11-24：用户实测确认持久 Bot 出现在地图中，修复后正常站在地面，标记 1.1 完成。本次反馈确认了地图可见性和站姿，未单独记录账号互斥和停服回登结果。

1. 用专用普通账号建立角色，记录角色 ID，离线前把它放在普通城镇地图。首次使用建议使用测试数据库。
2. 在配置文件设置 gms.ai.enabled 和角色 ID，按平常方式从 IDEA 启动。默认关闭。
3. 用另一个账号进入该角色所在世界、频道 1 和同一地图，核对名字、位置和装备。机器人这一阶段保持站立。
4. 尝试登录专用账号，预期收到账号已登录提示。正常停服后保留配置并重启，角色应重新出现。
5. 正常停服、将 gms.ai.enabled 改为 false，再重新启动。用专用账号登录，核对角色 ID、地图及原有角色数据。子里程碑 1.1 没有自动战斗、拾取或任务动作，因此经验与背包应保持原数据。

## 子里程碑 1.2 进度

同图步行使用 WZ 平台连接和 Dijkstra。移动执行逐段更新服务端坐标，并发送 053 动作包。可在现有 gms.ai 节点临时配置 walk-target-x 和 walk-target-y，取同一地图、与出生点平台相连的地面坐标。托管角色上线 15 秒后执行一次。到达和不可达分别记录 reached 和 cannot walk，移除这两个配置后恢复站立。游戏内表现待验证，跳跃、落下、梯绳和跨图待实现。

## IDEA 配置方式

编辑 gms-server/gms-handler/src/main/resources/application.yml 中现有的 gms.ai 节点。也可以在当前启用的 application-<profile>.yml 中覆盖这两个值。避免在同一个 YAML 文件重复创建 gms 节点。

```yaml
gms:
  ai:
    enabled: true
    character-id: 123
```

把 123 换成专用账号下真实角色的数字 ID，直接运行原有的 ServerApplication 启动配置。默认关闭。测试时观察日志 Persistent bot started for character；保存失败时保留 Error saving chr 日志。关闭时把 enabled 改回 false 并重启。

## 后续行为的代码形状

下面是后续阶段的设计示意。每个行为只读取角色快照并给出建议。游戏适配层在执行前重新检查目标是否仍存在、冷却是否结束、背包和地图状态是否仍符合条件。

```java
interface BotBehavior {
    Optional<ActionProposal> propose(BotSnapshot state);
}

Optional<ActionProposal> choose(BotSnapshot state, List<BotBehavior> behaviors) {
    return behaviors.stream()
            .flatMap(behavior -> behavior.propose(state).stream())
            .max(Comparator.comparingInt(ActionProposal::priority));
}
```

例如回城补给可以拆成寻找可达商店、通过传送口、接近 NPC、购买和喝药。地图移动、购买和物品使用各自可被其他行为复用。固定技能 ID 和红蓝药阈值放在角色行为配置中，游戏规则负责拒绝不合法的技能或药品操作。模型只在需要选择较长目标或回复聊天时介入。

第一阶段运行假设为单服务端进程及专用账号，此托管锁只在当前进程内生效。关闭托管再登录时，数据库是角色唯一的数据来源。现有存档接口自行记录数据库错误，重启验收应同时核对数据库保存日志和重新登录后的数据。
